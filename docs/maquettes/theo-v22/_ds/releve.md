# Relevé design system — maquettes Théo V22 (lecture seule)

Lot `THEO-V22-DS-RELEVE2`, 22/10/2026. Aucun code produit : ce document prépare le lot « design system » qui appliquera Théo V22 dans `packages/ui`.

## 0. Méthode et ce que les maquettes sont

- **Sources** : `Bellum_V22_Produit_Complet.html`, `Bellum_V22_BPCE.html`, `Bellum_V22_Onboarding.html` (branche `claude/maquettes-theo-v22`, lues sans être ajoutées). Les trois fichiers sont **identiques à 4 lignes près** : seul le script de route par défaut change (`#/chat`, `#/accounts/a-bpce`, onboarding). Un seul relevé suffit ; les chiffres ci-dessous viennent du « Produit Complet ».
- **Lecture** : `data:`/base64 retirés (2,5 Mo → 2,4 Mo), 22 blocs `<style>` extraits, valeurs finales lues en **styles calculés** (playwright sans tête, 1440×900 et 390×800, 18 routes, clair et sombre).
- **Le CSS est une pile de strates** (V2, « Discover V3 », a4, m5, t8, v7, v12, v13, a14, ac20, v22…) : la même règle est redéfinie jusqu'à 6 fois, la dernière gagne. Le **vrai** jeton est donc la valeur calculée, pas la première `:root` du fichier (qui date de la strate 1 : `--bg:#fff`, `--r:14px`, ici ignorés). Les tableaux ci-dessous donnent les valeurs **calculées**.
- **Bascule clair/sombre** : le HTML démarre en `class="dark"` et des scripts tardifs le re-posent à chaque rendu ; la seule bascule qui tient est **Réglages → Apparence** (`input[name=theme]` clair/sombre/système, puis « Enregistrer »). C'est ainsi que le clair a été mesuré.
- **Contraste** : WCAG 2.x, texte normal 4,5:1 (3:1 si ≥ 24 px ou ≥ 18,66 px gras), composant d'interface 3:1. Deux mesures : (a) couples de jetons (calcul exact) ; (b) éléments réellement rendus par écran (fond effectif composé sur les ancêtres — les fonds image/avatar donnent quelques faux positifs, signalés).

## 3. MOUVEMENT

### 3.1 Ce que fait Théo

- **Transitions** (71 déclarations) : `background/border-color/color/box-shadow` à **.12, .13, .14, .15, .16, .18, .2 s** ; `opacity 100ms` ; `transform .15/.18 s` (survol de carte : `translateY(−2 px)` ou `−3 px` + ombre) ; 11 règles `transition: none !important` + 17 blocs `prefers-reduced-motion` (bon réflexe).
- **Animations** (7 `@keyframes`) : `toast-in` 180 ms `translateY(8px)`→0 + fondu ; `fade-in` 130 ms `translateY(2px)` ; `v7-dialog-in` 170 ms `translateY(6px)` ; `v7-panel-in` 160 ms ; `v7-menu-in` 120 ms `translateY(−3px)` ; `v22-enter` 120 ms fondu .7→1 ; `d3-spin` **0,7 s linéaire infini**.
- **Courbes** : `cubic-bezier(.2,.7,.3,1)` (`--v22-ease`) et `cubic-bezier(.2,.7,.25,1)` (`--v7-ease`) ; reste en `ease`/`ease-out`.
- **Pas de rebond, pas de parallaxe, pas de ressort** ; `scroll-behavior:auto` (un `smooth` marginal). `scale(.8|.9)` : 2 occurrences (pastille).

## 5. Limites de ce relevé

- Le contraste « rendu » ignore les fonds image/dégradé (quelques faux positifs signalés) et ne mesure pas les états survol/focus (lus dans le CSS, non rendus).
- Les compteurs « décl. » sont des occurrences dans le CSS de la maquette (la même règle redéfinie par strate compte plusieurs fois) ; les mesures « rendu » sont les chiffres fiables.
- Les maquettes ne contiennent ni galerie ni page de composants : l'inventaire est induit des écrans.
