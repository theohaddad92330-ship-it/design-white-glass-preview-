## 1. ORION V12 est-il le successeur de DATAFORGE V10 ?

**Oui.** Comparaison colonnes/identifiants/grain, mesurée directement sur les
fichiers :

- **Même espace de clés.** `account_id` du pack ORION (format `DF-XXXX`) est
  strictement le même identifiant que `bellum_account_source_id` /
  `dataforge_accounts.source_id` du pack DATAFORGE V10 déjà ingéré (vérifié :
  `DF-0001` = Société Générale des deux côtés).
- **Même grain compte × domaine.** `3_ANALYTIQUE/30_FAIT_COMPTE_DOMAINE_V10.csv`
  fait 78 870 lignes = 1 195 comptes × 66 domaines — EXACTEMENT le volume du
  CSV canonique à 158 colonnes que `ingest-dataforge.ts` sait déjà parser.
- **C'est une décomposition normalisée du MÊME fichier**, pas un second jeu de
  données : le README du pack le dit lui-même (« Le V10 a été normalisé... »)
  et je l'ai vérifié colonne par colonne :
  - `30_FAIT_COMPTE_DOMAINE_V10.csv` (36 col.) = le sous-ensemble `bellum_*` +
    `domain__*` du CSV à 158 colonnes qui **varie** par compte × domaine ;
  - `31_DIM_DOMAINE_V10_66.csv` (66 lignes, 27 col.) = exactement les familles
    `domain_taxonomy__*` / `domain_gap__*` / `talent_supply__*` / `tjm__*` que
    `dataforge-columns.ts` documente déjà comme **constantes par domaine**
    (commentaire GA-37 du dépôt, écrit avant ce lot) — le pack a fait, à la
    source, la même normalisation que ce dépôt avait déjà déduite du fichier
    brut ;
  - `13_COMPTES_ATTRIBUTS_V10.csv` (1 195 lignes, 80 col.) = les colonnes
    `account__*` du même fichier, dédupliquées (elles étaient répétées 66 fois).

**Conclusion et décision** : je **n'ai PAS ré-ingéré** `30_FAIT_COMPTE_DOMAINE_V10.csv`
/ `31_DIM_DOMAINE_V10_66.csv` / `13_COMPTES_ATTRIBUTS_V10.csv` dans ce lot — ce
sont les priorités 4 à 6 de la tâche, pas les 3 retenues, ET les ingérer via un
second pipeline aurait dupliqué `dataforge_accounts` /
`dataforge_account_domains`. Si un futur lot veut les ingérer, la bonne porte
est d'ÉTENDRE `ingest-dataforge.ts` / `dataforge-columns.ts` pour accepter ce
format normalisé en ENTRÉE ALTERNATIVE au CSV à 158 colonnes (même sortie,
deux formats source) — jamais une seconde table.

Les trois capacités RETENUES dans ce lot (`10_COMPTES_MASTER.csv`,
`50_CHUNKS_INDEXABLES.csv`, `60_ANOMALIES_ET_CORRECTIONS.csv`) sont, elles,
**nouvelles** : DATAFORGE V10 ne portait ni statut de sales-readiness, ni
chunks RAG, ni registre qualité. Elles vivent dans TROIS tables neuves,
partagées (GA-16), reliées à `dataforge_accounts` par le même `source_id` mais
SANS contrainte FK (les deux packs s'ingèrent indépendamment).

## 4. Les sept avertissements, un par un

1. **Prior ≠ evidence (97,5 % Tier D).** Ne s'applique pas directement aux 3
   tables ingérées (aucune ne porte `bellum_evidence_tier`) — c'est la doctrine
   de `dataforge_account_domains`, déjà tenue par GA-37 et non touchée ici.
2. **Corrections V8 non propagées (AN-001).** Le registre `dataforge_data_anomalies`
   ingère le CONSTAT tel quel (y compris AN-001) — c'est un aveu documenté, pas
   une correction : l'anomalie EST le fait qu'Enedis/AXA/RTE/GRDF/ADEO portent
   encore l'erreur. Corriger les cellules elles-mêmes est hors périmètre (elles
   vivent dans `30_FAIT_COMPTE_DOMAINE_V10`, non ingéré ici).
3. **Taxonomies V9/V10 incompatibles.** Sans objet pour ce lot — aucune des 3
   tables ne porte de `domain_code`.
4. **Ne jamais sommer `internal_contacts_count`.** Documenté en commentaire sur
   `OrionAccountStatusRecord.internalContactsCount` et sur la colonne d'entité ;
   aucun service de ce lot ne calcule de somme sur ce champ.
5. **`[à rechercher V6]` / marque-places entre crochets ⇒ `null`.** Généralisé :
   `valueOrPlaceholderNull` (`orion-csv.ts`) traite TOUT texte entièrement
   entre crochets comme non-mesuré sur les champs typés concernés
   (`siren_siret`, `pf_consolide`, `procurement_page`, `supplier_portal`,
   `recommended_entry_point/persona/strategy`, `next_action`, `main_risk`,
   `source_quality`) — testé (`orion-csv.spec.ts`), et le texte brut du
   marque-place est PRÉSERVÉ dans `payload` (jamais perdu, juste déclassé).
6. **Anomalies lisibles depuis le produit, pas seulement documentées.** Les 20
   lignes de `dataforge_data_anomalies` ont un miroir 1:1 (même `code`) dans
   les 20 chunks `GARDE_FOU_QUALITE` de `dataforge_rag_chunks` — vérifié par
   `orion-anomalies-rag-parity.spec.ts` sur des données SYNTHÉTIQUES (le pack
   réel n'est jamais commité), avec les vrais parseurs de production. La
   capacité de recherche existe et est testée
   (`apps/ia/app/services/dataforge_rag_chunks.py`,
   `POST /rag/dataforge/search`) ; **son branchement dans le tour de
   conversation LIVE de Laura n'est PAS fait** — voir §10.
7. **Pénétrabilité = ordre de passage, pas verdict.** `OrionAccountsService.statusFor`
   est le SEUL point d'entrée qui lit `penetrabiliteScore`, et son retour
   groupe TOUJOURS `{ score, couvertureTotale, caveat }` — impossible
   structurellement d'obtenir le score sans sa couverture. Gardé par
   `orion-penetrabilite-jamais-nue.spec.ts` (scan de tout `apps/api/src`, hors
   liste blanche).

⚠️ Règle de jointure (partielle par construction) : respectée par construction
— aucune des 3 tables ingérées ne fait d'`INNER JOIN` avec `dataforge_accounts`
(le rejoint se fait par égalité de `source_id`, en lecture, jamais en jointure
SQL bloquante côté ingestion).
