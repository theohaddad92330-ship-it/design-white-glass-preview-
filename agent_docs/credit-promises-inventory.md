# Inventaire des promesses « crédits » — site, Stripe, API, backoffice

> **Objet.** L'audit comptable (`agent_docs/credits-accounting-audit.md`, §0) a établi que la
> page de vente décrit un modèle de crédits qui n'existe pas dans le code. Ce document est
> l'**inventaire exhaustif du côté promesse** : tout ce que BellumAI affirme à un client,
> où c'est écrit, ce que le code fait réellement, et où les deux divergent.
>
> **Il ne corrige rien.** Aucune ligne de copy marketing, de prix ou de code d'enforcement
> n'a été touchée. C'est un préalable à l'unification sur un compteur unique : tant que ce
> qui est VENDU n'est pas tranché, unifier ne produira qu'un chiffre de plus qui contredit
> les autres.
>
> **Périmètre couvert ici** : `apps/website` (site public), Stripe tel qu'il existe dans le
> repo, `apps/api` (catalogue + enforcement), `apps/dashboard-manager` (backoffice). Le
> volet `apps/web` est repris de l'audit et **revérifié** sur cette branche (les numéros de
> ligne ci-dessous sont ceux de `origin/main` @ `7fbe6fb4`, pas ceux de la branche d'audit).
>
> **Méthode.** Tout est établi par **lecture de code**. Aucun appel à l'API Stripe, aucune
> requête en base de production. Ce qui n'a pas pu être vérifié est marqué
> « aucune implémentation trouvée » — jamais déduit.
>
> Date : 2026-07-20 · Branche : `docs/credit-promises-inventory-2`

## ⚠️ À lire d'abord — exposition juridique et financière

Quatre points sont signalés **sans être corrigés**, car ils engagent l'entreprise et relèvent
d'une décision qui n'appartient qu'à vous.

### 1. Les CGV contredisent la page de vente, sur le point le plus cher

Le contrat que le client accepte dit **l'inverse** de la page qui lui a vendu le produit.

| Document                      | Ce qu'il dit                                                                                                                                                                                                                                          | Emplacement                                                                                                       |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| **CGV** (contractuel)         | « Certaines fonctionnalités de la plateforme, et notamment **les analyses d'entreprises, sont soumises à un système de crédits**. **Chaque analyse consomme un nombre déterminé de crédits** selon la formule d'abonnement souscrite par le Client. » | `apps/website/src/app/[locale]/cgv/page.tsx:1075-1078` (FR) · `:769-781` (EN) · `:137-150` (DE) · `:454-467` (NL) |
| **CGU** (contractuel)         | « **Crédit** : désigne l'unité de consommation permettant de **lancer une Analyse** sur la… »                                                                                                                                                         | `apps/website/src/app/[locale]/cgu/page.tsx:967` (FR) · `:687` (EN) · `:106` (DE) · `:399` (NL)                   |
| **Page pricing** (commercial) | « Analyse de compte — **Incluse · 0 crédit** »                                                                                                                                                                                                        | `apps/website/messages/fr/pricing.json:78` (+ en/de/nl, même ligne)                                               |
| **Page pricing** (commercial) | « L'analyse de compte est **toujours incluse** — les crédits ne sont consommés que lorsque vous déclenchez un enrichissement. »                                                                                                                       | `apps/website/messages/fr/pricing.json:73`                                                                        |

C'est le code qui est conforme aux **CGV**, pas au marketing. La page commerciale est donc
la pièce fausse — mais c'est elle que le client lit avant d'acheter.

Aggravant : les CGV renvoient à la page pricing pour connaître l'allocation
(`cgv/page.tsx:1077-1078`, « Le nombre de crédits inclus dans chaque formule est indiqué sur
la page de tarification du Site ») — or **la page pricing ne publie aucun solde de crédits** :
elle publie des quotas d'analyses et d'enrichissements. La clause renvoie à une information
qui n'existe pas.

### 2. Trois prix publiés ne sont pas implémentés — en quatre langues

`apps/website/messages/{fr,en,de,nl}/pricing.json:78, :88, :93` (fichiers byte-parallèles,
mêmes numéros de ligne dans les 4 locales ; locales actives et routées :
`apps/website/src/i18n/routing.ts:11`). Le site est **en production** sur `bellum-ai.com`
(`apps/website/README.md:3`). Détail en §1 ci-dessous.

### 3. Le client paie sur une page Stripe qui dit l'inverse du site

La description de la ligne d'abonnement, générée à chaque checkout :

```
name:        `BellumAI ${planConfig.label}`
description: `${planConfig.accounts_limit} analyses/mois, ${planConfig.enrichment_credits} enrichissements`
```

`apps/api/src/modules/credits/credits.service.ts:344-345`

Un client Team voit littéralement **« 50 analyses/mois, 100 enrichissements »** sur la page
de paiement et sur sa facture, après avoir lu que les analyses étaient incluses et gratuites.
Le même écart existe sur les recharges : le catalogue **vend des analyses à l'unité**
(`+5 analyses` 19 €, `+20 analyses` 59 €, `+50 analyses` 119 € —
`credits.service.ts:193-196`), ce qui est difficilement conciliable avec « 0 crédit ».

### 4. Fuite de revenu : une recharge d'analyses relève le plafond **à vie**

`grantTopup` incrémente `accounts_limit` (le plafond) et non un compteur consommable
(`credits.service.ts:594`), tandis que le reset mensuel remet `accounts_used` à 0 **sans
jamais restaurer `accounts_limit`** (`credits.service.ts:775-780`). Aucun chemin ne
réinitialise `accounts_limit`, hors nouveau checkout (`:458`) ou `assignPlan` admin
(`admin.service.ts:302-312`).

**Conséquence** : un pack « +50 analyses » acheté 119 € une seule fois augmente le quota
mensuel de 50 analyses **tous les mois, indéfiniment**. À 0,65 €/analyse, le pack est
rentabilisé par le client en deux mois et coûte ensuite 32,50 €/mois de COGS à perte.
Vérifié par lecture ; non testé en exécution. Ce point est aussi en contradiction avec la
clause CGV « Les crédits non utilisés […] ne sont pas reportables » (`cgv/page.tsx:1081-1084`).

## 0. Verdicts employés

| Verdict            | Sens                                                                                                        |
| ------------------ | ----------------------------------------------------------------------------------------------------------- |
| **conforme**       | Le code fait ce que la promesse annonce.                                                                    |
| **contredit**      | Le code fait quelque chose d'incompatible avec la promesse.                                                 |
| **non implémenté** | Aucune implémentation trouvée. La promesse ne repose sur rien.                                              |
| **ambigu**         | La promesse est vraie sous une lecture et fausse sous une autre, ou deux surfaces internes se contredisent. |

## 1. `apps/website` — le site public

**Locales : 4** — `fr` (défaut, sans préfixe), `en`, `de`, `nl`
(`apps/website/src/i18n/routing.ts:11-12`), 11 namespaces × 4 = 44 fichiers de messages.
L'audit avait raison sur ce point ; la contradiction apparente avec « 2 locales » venait de
`apps/web` (l'app produit), qui n'a effectivement que `en` + `fr`
(`apps/web/src/i18n/locales/{en,fr}`). **Les deux chiffres sont vrais, sur deux surfaces
différentes.**

**Les fichiers des 4 locales sont byte-parallèles** (131 lignes chacun pour `pricing.json`) :
chaque promesse porte le même numéro de ligne dans les 4 langues, et **aucun chiffre ne
diverge** entre locales. Toute erreur est donc publiée 4 fois.

### 1.4 D'où viennent les chiffres du site — hybride

- **Les prix sont live** : fetch de `GET /credits/plans` (`live-prices.ts:76`), cache ISR 300 s,
  fallback silencieux sur les chaînes du catalogue si l'API échoue (`live-prices.ts:111-112`).
  Commentaires explicites sur le risque (`PricingPlans.tsx:26-29`).
- **Les quotas, les coûts en crédits et le prix beta sont EN DUR** dans les JSON, dupliqués
  entre `pricing.json` et `home.json`, sans source partagée ni test de cohérence :
  quotas `pricing.json:30,46,62` + `:121` (prose FAQ) + `home.json:236,249,262` ;
  coûts crédits `pricing.json:83,88,93` + `home.json:129-131,134-136` ;
  beta `beta.json:4,18,75,126`.
- `ANNUAL_DISCOUNT` est **redéclaré** côté site (`live-prices.ts:19`) au lieu d'être importé
  de `packages/contracts` (le site ne dépend pas du package) — deux sources pour une constante.

| **2** | **« Ma carte affiche "Analyses illimitées" ET "120 analyses/mois (fair use)". »** Les deux libellés cohabitent sur la même carte (`billing-view-model.ts:93-94` vs `:99`), et le serveur n'a **aucun palier illimité** (`credits.service.ts:182`)                                                                                                                                                                                                  | 🔴 **Élevée**   | Contradiction **à l'écran, au même instant**, chez un client déjà payant. Un client Growth peut de bonne foi réclamer l'illimité qu'on lui affiche.                                                                                                                                     |
| **3** | **« Mon essai "complet" s'arrête en m'affichant "Quota atteint (0/40)". »** Le site promet 7 j « complets, toutes les fonctionnalités » (`pricing.json:109`) ; à l'expiration, le seul message est celui du quota (`analysis.service.ts:459-462`), qui annonce 0 consommé sur 40                                                                                                                                                                   | 🟠 **Moyenne**  | Touche le prospect au moment de la conversion, avec un message factuellement absurde. Aucun message « essai expiré » n'existe.                                                                                                                                                          |
| **4** | **« On me facture un téléphone 2 crédits. »** — en réalité **1** (`credits.service.ts:74, :102-105`)                                                                                                                                                                                                                                                                                                                                               | 🟠 **Moyenne**  | **Financièrement favorable au client** (il paie moitié moins qu'annoncé), donc peu de risque de réclamation. Le risque est l'inverse : un prix public inexistant, et un client qui a **budgété** sa consommation sur une grille fausse.                                                 |
| **5** | **« Le message personnalisé m'est facturé 1 crédit. »** — il est **gratuit** (`ia-proxy.controller.ts:190-202`)                                                                                                                                                                                                                                                                                                                                    | 🟠 **Moyenne**  | Favorable au client, mais le compteur « 4 crédits estimés » du site (`home.json:123`) surestime de 100 % le coût réel d'un panier type : le client sous-dimensionne son offre par prudence, donc **vous perdez du MRR**. Et les 6 routes LLM restent non plafonnées (coût non couvert). |
| **6** | **« Vos CGV disent que les crédits ne sont pas reportables, mais mon solde d'enrichissement se cumule. »** `GREATEST(enrichment_credits, quota)` (`credits.service.ts:777`) vs `cgv/page.tsx:1081-1084`                                                                                                                                                                                                                                            | 🟡 **Faible**   | Favorable au client, personne ne s'en plaindra. À corriger dans le sens des CGV **ou** l'inverse, mais sans urgence.                                                                                                                                                                    |
| **7** | **« La page beta promet un tarif gelé à 59 € »** (`beta.json:75, :85`), prix **entièrement en dur**, hors système de prix live, page indexée en sitemap priorité 0.9                                                                                                                                                                                                                                                                               | 🟡 **Faible**   | Aujourd'hui exact (`plan-catalog.defaults.ts:137`). Deviendra faux silencieusement si le palier beta est édité — et « gelé pour la durée du programme » est un engagement de durée.                                                                                                     |

**Griefs qui ne viennent pas d'un client mais vous coûtent de l'argent** (hors classement) :
la recharge d'analyses qui relève le plafond à vie (§⚠️4) ; les 6 routes `/ia/*` non facturées
ni plafonnées ; `assignPlan` qui peut créer un essai perpétuel (`admin.service.ts:302-312`) ;
le prix du siège inéditable (`route.ts:12`).

### 6.3 Ce qu'il faut trancher avant d'unifier

Ces décisions vous appartiennent : elles fixent ce que vous **vendez**, pas comment on le code.
Chacune est présentée en options avec leurs conséquences vérifiées, sans recommandation.

---

**D1 — L'analyse est-elle gratuite ou facturée ?** _(bloquant : tout le reste en découle)_

| Option                                                                               | Conséquence                                                                                                                                                                                                                                                                                                                                                                                          |
| ------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **a)** Le code rattrape le site : l'analyse devient réellement gratuite hors plafond | Le poste à **0,65 €/run** (`pricing-proposal.md:38`) n'est plus couvert par une unité vendue. Il faut alors un plafond dur assumé et affiché — donc « gratuit » redevient « inclus jusqu'à N », c'est-à-dire ce que fait déjà le code. Impose aussi de réécrire les CGV (`cgv/page.tsx:1075-1078`) et de renoncer aux recharges d'analyses (`credits.service.ts:193-196`, un produit déjà vendable). |
| **b)** Le site rattrape le code : l'analyse consomme, et on l'affiche                | Réécriture de 5 emplacements × 4 langues + le widget « 4 crédits » (`home.json:123`). Le slogan « Payez uniquement ce qui compte » (`pricing.json:72`) et l'argument « analyse incluse » tombent — c'est l'accroche commerciale actuelle. **Aligne site, code et CGV d'un coup.**                                                                                                                    |
| **c)** Compteur unique pondéré (§7 de l'audit : 1 analyse = 8 crédits)               | Un seul nombre pour le client, cohérent avec les CGV telles qu'elles sont écrites, marge préservée à ±0,5 %. Mais **tous** les libellés changent (site, app, DM, Stripe), et les poids 🟠/🔴 de l'audit ne sont pas mesurés : l'audit pose lui-même comme prérequis d'instrumenter le coût réel avant de figer la grille.                                                                            |

**D2 — La tarification par type de donnée (email 1 / téléphone 2) existe-t-elle ?**

| Option                          | Conséquence                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **a)** L'implémenter            | Il faut élargir `EnrichmentType` (`credits.service.ts:74`) et threader un `type` dans les 2 sites d'appel. **Obstacle de fond** : le débit est **post-succès** et un enrichissement retourne ce qu'il trouve — email, téléphone, ou les deux. Il faut donc décider ce qu'on facture quand un appel rend **les deux** (1 ? 2 ? 3 ?), alors que le site promet un « coût affiché **avant** le clic » (`pricing.json:89`) qui n'est pas connaissable avant l'appel. |
| **b)** Retirer la ligne du site | Simplification immédiate, grille honnête. À vérifier avant : si « téléphone = 2 crédits » figure dans un deck ou a été dit en clientèle, c'est un engagement pris hors du site.                                                                                                                                                                                                                                                                                  |

**D3 — Le message personnalisé est-il payant ?**

| Option                                        | Conséquence                                                                                                                                                                                    |
| --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **a)** 1 crédit, comme annoncé                | Il faut brancher `CreditsService` dans `ia-proxy` (module qui n'en importe rien aujourd'hui) — 6 routes concernées, pas seulement `/ia/message`. Rend la promesse vraie et couvre le COGS LLM. |
| **b)** Gratuit, et on retire la ligne du site | Le plus simple. Mais la surface `/ia/*` reste **non plafonnée** (D4 de l'audit) : coût non borné, non mesuré (l'audit le classe 🔴 « jamais mesuré »).                                         |
| **c)** Gratuit mais rate-limité               | Compromis proposé par l'audit (§7). Demande de fixer un plafond par workspace, chiffre qui n'existe pas encore.                                                                                |

**D4 — « Illimité » doit-il exister ?** Le code dit non, explicitement (`credits.service.ts:182`).

| Option                                                                                                         | Conséquence                                                                                                                                |
| -------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| **a)** Supprimer les 3 libellés (`fr/billing.json:22, :178, :182`) et la sentinelle `999_999` (4 emplacements) | Supprime la contradiction n°2 du classement. Sans effet commercial : aucun palier vendu ne déclenche ces libellés aujourd'hui.             |
| **b)** Créer un vrai palier illimité                                                                           | COGS non borné (0,65 € à 1,08 € par run selon l'audit). Contredit la décision Théo §14/§7 déjà inscrite dans le code (`plans.ts:119-120`). |

**D5 — Le périmètre de l'essai.** Aujourd'hui 40/75 — plus généreux que Starter (15/20) et
proche de Team (50/100). Le garder tel quel (argument de conversion fort, mais un prospect
peut consommer l'équivalent de 26 € de COGS gratuitement) ou l'aligner sur Starter (cohérent
avec « puis choisissez le forfait », moins démonstratif).

**D6 — Les recharges d'analyses relèvent le plafond à vie** (`credits.service.ts:594` + `:775-780`).
Bug à corriger (le pack ne vaut que pour le mois) **ou** comportement voulu (vous vendez un
upgrade permanent à 119 €) ? Les deux lectures sont défendables, l'écart de revenu est
considérable, et le libellé Stripe actuel (« 50 analyses supplémentaires »,
`credits.service.ts:1186`) suggère la première.

**D7 — La reportabilité.** Les CGV disent non-reportable ; le code reporte les enrichissements.
Aligner le code sur les CGV, ou les CGV sur le code (le report est un argument commercial).

**D8 — La source de vérité des quotas affichés.** Les **prix** du site sont live
(`live-prices.ts:76`), les **quotas** sont en dur dans 4 langues × 2 pages, sans test de
cohérence. Les tokeniser comme `{seatPrice}` (le site suit le catalogue automatiquement) ou
assumer la dérive (et ajouter un test qui compare le JSON au catalogue).

**D9 — Qui peut changer un prix, et avec quels garde-fous.** Le catalogue est éditable en
production avec pour seule validation « entier ≥ 0 » (`plan-catalog.service.ts:185-187`) :
rien n'empêche de mettre Growth à 0 €. Par ailleurs une édition de quota d'enrichissement est
**rétroactive** pour tous les abonnés (via le reset mensuel, `credits.service.ts:771`) alors
qu'une édition de quota d'analyses ne l'est **pas** (plafond gelé par abonné). Cette asymétrie
n'est documentée nulle part côté client.
